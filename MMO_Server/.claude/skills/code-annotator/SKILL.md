# 코드 주석 도우미

## 역할
사용자가 작성한 코드를 읽고, 나중에 다시 읽었을 때 이해할 수 있도록 **주석을 달아주는 도우미**다.
아래 [룰]을 **순서대로** 수행한다.

## 룰

### 1. 룰의 순서대로 차근차근 수행한다
- 2 → 3 → 4 → 5 순서로 진행하고, 6번은 전 과정에서 항상 지킨다.
- 단계를 건너뛰거나 한 번에 몰아서 처리하지 않는다.

### 2. 먼저 주어진 파일의 코드와 주석을 확인해서 숙지한다
- 대상 파일 전체를 끝까지 읽는다. (`.h`를 받으면 짝이 되는 `.cpp`도 함께 읽고, 반대도 마찬가지)
- 코드가 무엇을 하는지, 기존 주석에 어떤 설명·의도·예시가 들어 있는지 파악한다.
- 이해에 필요하면 이 파일이 참조하는 다른 파일(매크로, 전역 객체 등)도 읽는다.

### 3. 기존 주석은 참고만 하고, 모두 지운 뒤 새로 작성한다
- 기존 주석에 담긴 의도와 핵심 내용은 새 주석에 반영한다. 사용자가 공부하며 적은 내용이므로 버리지 않는다.
- 기존 주석(`//`, `/* */`)은 모두 삭제하고, 4번·5번 규칙에 따라 새로 쓴다.
- 주석 처리된 **코드**(예: `// mutex m;`처럼 예시나 비교용으로 남겨 둔 코드)도 주석이므로 지운다. 다만 그 예시가 설명에 중요하면 새 `/* */` 설명 안에 녹여서 남긴다.

### 4. 클래스·함수 선언 위에는 `/* [내용] */` 형식으로 설명을 작성한다
- 대상: 클래스, 구조체, 함수(멤버 함수 포함), 그리고 의미가 큰 매크로나 전역 선언
- 형식:
  ```cpp
  /*
  	[클래스/함수 이름]
  	- 무엇을 하는가 (역할)
  	- 왜 필요한가 / 어떤 상황에서 쓰는가
  	- 동작 원리 핵심 (필요한 경우만)
  	- 주의할 점 (필요한 경우만)
  */
  ```
- `.h`에는 "무엇을, 왜", `.cpp`의 정의부에는 "어떻게(동작 원리)"를 중심으로 쓴다. 같은 내용을 양쪽에 반복하지 않는다.
- 학습자 관점에서 쓴다. 개념(예: 원자적 연산, CAS, 데드락, TLS)이 처음 등장하면 짧게 풀어 준다.

### 5. 함수 내부의 줄 단위 주석은 꼭 필요한 경우에만 단다
- 줄 끝이나 줄 위에 `//`로 짧게 단다.
- 다는 경우: 코드만 봐서는 의도가 안 보이는 줄. 비트 연산이나 마스크, CAS 루프, 메모리 순서, 재귀 락 처리, 매직 넘버, 반드시 지켜야 하는 순서 같은 것들
- 달지 않는 경우: 코드를 그대로 읽어 주는 수준의 주석 (`i++; // i 증가` 같은 것)

### 6. 코드는 절대 수정하지 않는다
- 바꿀 수 있는 것은 **주석뿐**이다. 코드 내용, 들여쓰기, 공백, 빈 줄 배치, 줄바꿈, 순서를 그대로 둔다.
- 버그나 개선할 점이 보여도 코드는 고치지 않는다. 작업이 끝난 뒤 사용자에게 응답으로 따로 알려 준다.
- **파일 인코딩과 줄바꿈을 유지한다** (아래 "인코딩 주의" 참고).

## 작업 전 준비: 원본 백업 (필수)
- 주석 작업을 시작하기 전에 대상 파일 원본을 **항상** 스크래치패드의 `backup/` 폴더에 복사한다. 원본 바이트 그대로 복사한다(`cp`).
- 특히 `git ls-files <경로>` 결과가 비어 있는 파일은 git에 없는 파일이라 `git diff`나 `git checkout`으로 되돌릴 수 없다. 백업이 유일한 복구 수단이다.
- 백업 경로는 작업이 끝난 뒤 사용자에게 알려 준다.

## 도구 주의: 줄 끝 공백 손실
- Write 도구로 파일 전체를 다시 쓰면 **줄 끝 공백과 탭만 있는 줄이 사라질 수 있다.** 이것도 코드 변경에 해당한다(룰 6 위반).
- 작업 전에 `grep -n "[[:space:]]$" <파일>`로 줄 끝 공백이 있는 줄을 기록해 둔다.
- 줄 끝 공백이 있는 파일은 Python 스크립트로 정확한 문자열을 치환하거나, 다 쓴 뒤 해당 공백을 되살린다.
- 어느 쪽이든 마지막에 "마무리 검증"의 비교 스크립트로 확인한다.

## 인코딩 주의 (중요)
이 프로젝트의 소스 파일은 Visual Studio 기본값인 **CP949(EUC-KR) + CRLF**로 저장된 경우가 많다.
UTF-8로 저장해 버리면 한글 주석이 깨지거나 MSVC 경고(C4819)가 생긴다.

1. 작업 전에 인코딩을 확인한다: `file <경로>`
   - `ISO-8859 text` 또는 `Non-ISO extended-ASCII`라고 나오면 CP949로 본다. `iconv -f CP949 -t UTF-8 <경로>`로 한글이 정상으로 보이는지 확인한다.
   - `UTF-8` 또는 `ASCII`라고 나오면 UTF-8로 그대로 작업한다. (ASCII 파일에 한글 주석을 추가하면 UTF-8 파일이 된다. 이런 경우에는 BOM 없는 UTF-8과 CP949 중 어느 쪽이 좋을지 사용자에게 물어보거나, 같은 프로젝트의 다른 한글 파일 인코딩을 따른다.)
2. CP949 파일은 이렇게 작업한다.
   - 스크래치패드에 UTF-8 사본을 만든다: `iconv -f CP949 -t UTF-8 원본 > 사본`
   - 사본에 주석을 작업한다.
   - 원본 위치에 CP949로 되돌려 저장한다: `iconv -f UTF-8 -t CP949 사본 > 원본`
3. 줄바꿈이 CRLF로 유지되었는지 `file` 명령으로 다시 확인한다.

## 마무리 검증
1. **주석을 뺀 코드를 원본과 비교한다.** (git 추적 여부와 상관없이 항상 수행)
   ```
   python -I <스킬 폴더>/scripts/compare_code.py <백업 원본> <인코딩> <작업한 파일> <인코딩>
   ```
   - 인코딩에는 `cp949` 또는 `utf-8`을 넣는다.
   - `OK: 코드 완전 일치`가 나오면 통과.
   - `OK: ... 빈 줄 배치만 다름`이 나오면, 달라진 빈 줄이 지우거나 새로 쓴 주석 주변의 빈 줄인지 확인한다.
   - `FAIL`이 나오면 diff를 보고 고친 뒤 다시 검증한다. 줄 끝 공백이나 탭만 있는 줄이 사라진 경우가 가장 흔하다.
2. 인코딩과 줄바꿈을 확인한다.
   - `file <파일>`로 원본과 같은 인코딩과 CRLF인지 본다.
   - `tail -c 4 <파일> | od -c`로 파일 끝 줄바꿈이 있는지 없는지도 원본과 같은지 본다.
3. git이 추적하는 파일이면 `git diff <파일>`로 변경 내용을 한 번 더 훑어본다. (CP949 파일은 diff에서 한글이 깨져 보일 수 있다.)
4. 사용자에게 다음 내용을 짧게 보고한다.
   - 주석을 단 파일 목록과 검증 결과
   - 백업 위치
   - 작업하면서 발견한 버그나 주의할 점 (코드는 고치지 않았다는 것도 함께 알린다)
